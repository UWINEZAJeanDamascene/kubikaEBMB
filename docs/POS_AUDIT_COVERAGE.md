# POS audit coverage inventory

Last reviewed: 2026-11-11

## Recording contract

- A committed state change must write its domain success event through the same PostgreSQL transaction client that commits the change. If the transaction rolls back, neither the change nor its success event remains.
- An authenticated POS write that returns a 4xx or 5xx response is handled once by `middleware/posAuditOutcome.js`. Denials use `writePosDenialAudit`; failures use `POS_ACTION_FAILED`. A domain-specific PIN or invalid-voucher denial suppresses the duplicate generic denial event.
- Denial counters are scoped by company, register, actor, event, and action. Redis provides a shared 60-second counter with a 24-hour TTL where configured; a bounded process-local counter is the explicit fallback. The first five attempts in a window each get an audit row, then rows are sampled at powers of two. Every sampled row includes `attemptCountInWindow`, the window start, and whether its counter was shared or instance-local. This bounds audit writes to logarithmic growth during a denial flood while retaining a count at each emitted sample. If an instance stops before another sample threshold, the final sub-threshold attempts are not represented in the audit-row estimate.
- Failed PIN and invalid-voucher attempts use the same sampling policy. PIN lockout events remain individually recorded when a lockout is reached. Their existing lockout controls still enforce behavior; audit sampling does not weaken or replace those controls.
- The manager security report weights sampled event rows by their latest count in each counter window. If the counter ran instance-local, the report labels are still meaningful but the count may be a lower bound across multiple server instances. Production-wide exact counts require configured Redis.
- Successful responses are not given a generic success event. The action's domain event is the success record; this avoids double-logging a single action.
- The shared outcome record contains only route template, status, response error code, actor, company, register, IP, and time, plus the denial counter window metadata. It never stores the request body, password, PIN, approval token, customer details, or payment credentials.
- Unauthenticated requests without a trustworthy company/actor context cannot be attached to a tenant audit stream. Authentication and PIN flows with a known company/user write their own denial events.
- If the audit database itself is unavailable, the original response is preserved and a server error is logged for monitoring. This is an operational audit-write failure, not a successful audit.

## Structured event record

New hash-chain rows use hash version 2. In addition to the event name and sanitized metadata, each row stores `action_id`, `correlation_id`, `outcome`, `entity_type`, and `entity_id` as queryable columns. These fields are included in the v2 row digest. Existing immutable rows are not rewritten: rows with a null hash version retain their original v1 digest and remain verifiable.

`action_id` identifies one emitted audit event. `correlation_id` links multiple events from one approval or business workflow. `outcome` is constrained to `COMMITTED`, `DENIED`, `FAILED`, or `OBSERVED`. The writer infers common affected entities from allowlisted metadata keys, and callers may supply explicit entity fields where inference is insufficient. Sensitive values continue to be redacted from metadata; entity fields contain identifiers only.

The columns improve filtering and correlation; they do not alone enforce exactly-once emission. Exactly-once is proven only for operations with a stable idempotency boundary plus focused transactional tests. See [the sales and financial mutation matrix](pos/financial-audit-matrix.md) for that scope. The configuration, customer, voucher, loyalty, EBM, and receipt matrix below records current event ownership and proof status.

## Verification status and limits

Coverage now includes:

- `test/posAuditIntegrityService.test.js` verifies hash and checkpoint tampering in the verifier.
- `test/posAuditDatabase.integration.test.js` exercises database update/delete rejection and transaction rollback when the chain-required insert trigger rejects an audit row. It runs only when `POS_TEST_DATABASE_URL` points to a local database ending in `_test` or `_scratch`, and that database has the audit migration applied.
- `test/posAuditService.test.js` proves the audit writer propagates a failed write to its caller transaction; the database integration case proves that the transaction does not retain its staged idempotency reservation or audit row.
- `test/posRouteSecurity.test.js` scans every route in the six configured POS/till/sales/credit-note/payment-settings/print-agent routers and fails for missing auth, authorization, duplicate declarations, or a mutation without shared idempotency or a documented native boundary.
- `test/posIdempotencyService.test.js` verifies a completed request replays without invoking the action again, an in-flight duplicate is blocked, and a key reused for different payload is rejected.
- `test/posSaleCompletionPostgres.integration.test.js` proves one sale, payment, receipt number, and journal entry across concurrent retries and a lost acknowledgment, when run against the explicit local scratch database.

These checks strengthen the proof but do not establish exactly-once database effects for every POS business operation. The route inventory proves each configured mutation has a replay boundary, while the shared middleware test proves request handling behavior; domain-specific database effects still need focused integration tests per operation family. The existing sale-completion PostgreSQL test is the end-to-end exactly-once proof for sale completion, not refunds, account payments, cash movements, stored-value operations, settings, or every other mutation. Native device/offline/provider boundaries also require their own integration tests. The inventory does not cover dynamically mounted routers outside the six listed files.

The generic outcome hook makes authenticated write denials and server failures visible in the existing **POS Back Office → Audit log** view. It is mounted on `/api/pos`, `/api/sales-legacy`, and `/api/tills` before route handlers, and the view already supports filtering by event name. Search for `POS_ACTION_DENIED` or `POS_ACTION_FAILED` to review these outcomes. Domain success events remain visible there under their action-specific event names.

The append-only hash-chain verification remains available through `services/posAuditIntegrityService.js` and its scheduled checkpoint verifier. Its database migration is still unapplied until the operator deploys it; do not treat a database without that migration as hash-chain protected.
