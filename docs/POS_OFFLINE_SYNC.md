# POS offline queue and payment flow

POS offline sales are stored locally in encrypted IndexedDB records. Saving a sale, its outbox operation, its dependency on the previous device operation, and the per-device sequence is atomic. Existing queued operations are migrated as `LEGACY`; a migration never changes the payment flow of a saved sale. The approved operation types remain deliberately limited to `SALE_COMPLETE` and `CASH_MOVEMENT`; the latter is restricted to `cash_in`, `cash_out`, and `safe_drop`. Refunds, voids, discounts, price overrides, and other actions are not added to the offline contract.

The server-signed offline snapshot binds the cashier, device, register, warehouse, till session, expiry, and effective payment flow. The queued sale keeps that flow and its stable operation ID through synchronization. A changed or unavailable flow is surfaced as a review exception; synchronization does not fall back to another checkout path.

## Offline payment and cash-movement policy

Offline sales accept up to five fully paid cash, manually captured card, and manual mobile-money tender lines. Card requires a transaction reference. Mobile money is limited to one payment per sale and requires a configured provider, transaction reference, payer phone, and cashier confirmation that funds were received. Same-action card amounts are aggregated for the per-transaction cap; the server reserves one usage row per operation and action. Non-cash tenders cannot exceed the server-calculated total, and any change must come from cash. Partial payment, discounts, price overrides, and other balance-checked tenders remain online-only. PAYMENTS_V2 sales are created pending, paid through the existing cash/card or manual mobile-money endpoints, and completed using stable idempotency keys derived from the same operation ID. The server validates the tender allocation against the calculated total before posting.

Company administrators configure per-transaction, per-offline-snapshot total, and count limits for mobile money, card, paid-in, and paid-out actions. Register overrides take precedence over till-type overrides, which take precedence over company defaults. Blank and zero limits block an action. The settings editor requires POS settings permission and records before/after values and the actor. A signed snapshot provides effective caps for local blocking; synchronization re-resolves the current server-side caps and records accepted usage in a company/snapshot/action ledger. The ledger allows one reservation per operation and action; only a retry with matching amount, device, register, and occurrence time is an idempotent replay. A conflicting retry is rejected, audited, and retained for review. An over-cap operation is retained as a review exception and is not posted.

Snapshot retention and cleanup policy is not yet defined, and there is no automatic snapshot cleanup. A snapshot with unsynchronized operations or cap-usage rows must never be purged. Deleting a snapshot cascades to its cap-usage rows, so any future retention job must preserve snapshots until neither condition applies.

Offline paid-in and paid-out drawer movements are signed outbox operations linked to the active shift. They use the same encrypted queue, sequence, and idempotency rules as sales and are rechecked against the corresponding action caps before the existing cash-movement controller posts them.

Offline tax calculations always use the signed snapshot rate and code; stale queued tax fields are ignored only when the resulting total matches the saved sale total. PAYMENTS_V2 pending sales retain their original total and tax fields, and completion backfills a missing total from the persisted pending invoice for older sales. For legacy encrypted queues without `displayTotal`, retry fills it from the locally persisted sale total. A total mismatch requires manager review. Batch-tracked items use FEFO allocation from the signed snapshot; each offline sale records the exact batch IDs and quantities. If an older queued sale has a signed snapshot without batch data, synchronization reconstructs a FEFO allocation from current eligible stock and marks the stock movement as reconstructed at sync. If a batch is missing, quarantined, expired at the reported sale time, or has insufficient unreserved stock when synchronization posts, the sale is recorded with its batch cost and an auditable batch conflict for manager review. Queued sales on the same snapshot reserve their batch quantities locally so later offline checkouts do not reuse them.

The register must still have a valid cashier session and open shift when synchronization posts the sale. Flow changes, missing sessions or shifts, and server-side validation failures require review; they never reroute through legacy checkout.

## Server sync protocol status

The authenticated `POST /api/sales-legacy/offline-sync/push` endpoint accepts up to 50 operations and returns an independent result for each. The open POS client splits larger recoveries into ordered batches of at most 50 and stops at the first batch with a non-success result. The open POS session and registered device token are required. Each canonical operation envelope is signed with the enrolled device's P-256 ECDSA private key; the server verifies it against that device's SPKI public key. The opaque device token remains an authentication credential and is stored server-side only as a SHA-256 hash. The server records an operation ledger keyed by company, device, and operation ID, and separately enforces sequence uniqueness. New local operations name the immediately preceding operation as a dependency. The server requires contiguous sequence order and refuses to post an operation while any predecessor is not synced; a review or quarantined predecessor blocks all later operations. Repeated completed operations replay the stored result. Clock skew is recorded, terminal checkout failures are retained in the exception table, and transient failures remain retryable. Known pre-creation failures for `POS_PAYMENT_V2_SEPARATE_PAYMENT_REQUIRED` and `POS_OFFLINE_RECEIPT_NUMBER_INVALID` can be retried with the same operation ID after correcting the request; receipt recovery permits changing only the receipt number, and a compare-and-set claim prevents concurrent retries. Success clears the old exception. Sale execution goes through the existing direct-sale and V2 completion controllers. The client applies per-operation results with capped exponential backoff and jitter; requests allow up to three minutes for cold starts.

The generic service-worker mutation queue explicitly bypasses all `/api/pos/*` and `/api/sales-legacy/*` requests. POS Background Sync, where available, only wakes an open application client; that client uses its normal session, enrolled device token, encrypted queue, and device signature. The worker does not receive or persist POS credentials or signing keys. Generic queued requests reject credential-bearing headers or JSON fields and persist only `Accept` and `Content-Type` headers.

## Device enrollment and lifecycle

POS devices are bound to a company and register. Enrollment stores the device public key and hashed token in `pos_devices`; only one device may be active on a register at a time. Existing register claim codes are one-use and short-lived. Supported app versions are checked during enrollment and on every queued operation.

Managers can list devices and enable, disable, revoke, or request a wipe through the `/api/till/devices` routes. Revocation ends the active POS session and leaves the device token available for contact: subsequent queued operations are recorded as exceptions and never posted. The device-state endpoint reports the pending wipe flag. A client must export any queued operations, or confirm the queue is empty, before acknowledging a wipe; the private signing key and local POS data are not removed before that gate.

ECDSA signatures detect payload edits and prevent another device from signing as the enrolled device. They do not prevent someone operating a live browser, so server-side validation, limits, and exception review remain necessary.

## Offline authentication and manager approvals

An online POS PIN login or cashier switch refreshes a device-bound verifier for that cashier. The verifier binds company, device, register, and cashier, and uses a random salt with PBKDF2-SHA-256; the PIN itself is never persisted. The verifier, offline session, failure counter, and pending failure reports are stored in the encrypted IndexedDB metadata store. The local PIN policy locks a cashier out after five failures for five minutes. A valid verifier is required to unlock offline; otherwise the till stays locked until a successful online login refreshes it.

Offline PIN failures are signed by the enrolled device key and include the verifier's signed capability. The client submits pending reports when connectivity returns and before the next online PIN login. The server verifies the device signature, capability scope, cashier assignment, and report time; report IDs make retries idempotent. Accepted reports update the server-side register PIN failure and lockout state and create audit events. Do not clear the device cache while failure reports or queued operations remain.

Offline manager approval is disabled by default. When enabled in POS settings, administrators can configure separate caps for card, mobile money, paid-in, and paid-out actions. A manager must first sign in online on the same device so their encrypted verifier and `pos.approve` permission are cached. The manager then approves with their PIN; the cashier PIN is not replaced. At sync the server rechecks the manager's active status, register assignment, permission, snapshot capability, action, amount, and current manager cap. An approved operation is recorded as `needs_review` and never auto-posted. The `20261107170000_pos_offline_manager_approval` migration expands the usage-ledger constraint for the separate manager cap buckets.

The till queue is view-only: it provides manual sync, a JSON export that leaves the queue intact, and a local X report explicitly marked unsynced. Provisional sale receipts can be printed using the shared receipt renderer and are labeled as not tax invoices. Logout, cashier switching, register changes, and shift close are blocked while that device has unsynchronized operations. A remote wipe exports queued data before removing the queue and signing key. Browser or operating-system controls can still erase site storage outside the application's control; staff should follow the export and queue-empty safeguards before clearing it.

Offline snapshot issuance allocates a block of 50 invoice references from the canonical company invoice sequence. A queued sale reserves one number from its authenticated device/register block; the sale transaction atomically consumes it, and replay returns the original invoice number. Unused references are extended on the next snapshot refresh and are never reused after consumption.

Price history is append-only and effective-dated for both standard product prices and price-list overrides. The migration backfills current values, and database triggers record subsequent inserts, edits, and removals. Offline checkout resolves the authorized price at the signed sale time and compares it with the signed catalog snapshot before invoice creation.

`GET /api/sales-legacy/offline-sync/pull` returns bounded, numeric-cursor deltas for catalog and warehouse stock, effective prices, customers, and POS offline settings. Database triggers record updates and tombstones; the POS persists a cursor per company, device, and warehouse and applies each page to its product, customer, settings, and IndexedDB caches while open. Cursor advancement follows cache application so failed local writes are retried.

PostgreSQL integration tests now cover concurrent duplicate delivery and lost-ack replay for processed operations, independent outcomes and exception persistence for partial batches, and payment/journal idempotency during sale completion. A client test uses a simulated slow connection to verify that the request times out with a retryable error while the queued operation remains available to the caller.

The integration suites require `POS_TEST_DATABASE_URL` to point to a local PostgreSQL database whose name ends in `_test`. For an explicitly approved local development database, `POS_TEST_ALLOW_LOCAL_DATABASE=true` enables the existing local-database guard. Fixtures use unique company/device IDs and clean up their rows. Migration `20261107140000_fix_pos_sync_warehouse_trigger` also prevents customer inserts from evaluating warehouse-only fields in the sync trigger.

Cold-start behavior and real mobile-network/browser interruption still need a device-level soak test before the Stage C real-world exit gate is complete.
